# Changelog

All notable changes to `evalyn-dashboard` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **Re-running a pinned job inherits the pin on the new entry.** Customer scenario: user pinned a reference run as a known-good baseline ("don't lose this one"). Re-running it before this change produced a fresh entry with `pinned=false`, so the next history-cap eviction would silently drop the rerun and the user's "keep this around" intent was broken on every re-run. Now both single-row Re-run and bulk Re-run inherit `entry.pinned` onto the upserted new entry. The chain of "the run I keep around" survives re-runs. No-op for unpinned source jobs (the `pinned: true` field is only spread when the source had it).
- **Skip OS notification on `cancelled`.** The user just clicked Cancel - a popup telling them their job got cancelled is at best redundant, at worst spammy. The `NotifyOpts.status` type now narrows to `'complete' | 'failed'` so the contract is enforced at the type level rather than carried in caller comments. The hidden-tab gate inside `notifyJobTerminal` is unchanged.

### Added

- **"tested 30s ago" timestamp on the per-provider Test result chip.** The Pass/Fail pill now sits next to a live relative-time label so the user can tell whether the chip reflects a fresh probe or a stale earlier click. Updates every 60s while a result is showing (no interval otherwise - idle pages stay quiet). Sub-minute granularity for the first minute (`just now` → `5s ago` → `30s ago`) since that's the window in which the user is actively waiting and the precision matters; minute / hour / day buckets after. `nowMs` is synced inside `handleTest` so the first render of the chip never shows a stale diff against a mount-time clock. Tooltip on the label has the absolute time for users who want exact wall-clock.
- **"Copy log URL" button in the CliRunner output toolbar.** Power-user share affordance for the new `?download=1` endpoint shipped this tick. One click copies an absolute URL like `https://dashboard.example/api/jobs/abc.../output.txt?download=1` to the clipboard - paste into Slack/email and the recipient gets the log as a save-as download. Absolute URL (uses `window.location.origin`) so the link stays meaningful when pasted across origins. Independent copy state from the other "Copy ..." buttons. Visible only when a `jobId` is set.
- **Help overlay (`?`) lists context-specific shortcuts.** The shortcuts I've shipped this loop weren't discoverable: `/` to focus the drawer search, `Cmd/Ctrl+L` to clear the runner output, `Cmd/Ctrl+Enter` to send a co-pilot message, `Cmd/Ctrl+S` to save annotations. They're now in a second section below the global ones, divided by a thin top-border. Each label includes the surface in parens (`Focus search (Recent Jobs drawer)`) so the binding's scope is obvious without sub-headers. The 5 global shortcuts (`Cmd K` / `Cmd J` / `Cmd ,` / `?` / `Esc`) keep their existing position.
- **"Export CSV" button in the Recent Jobs drawer footer.** Customer-cared data-portability win: drag the local drawer history into a spreadsheet for filtering, sharing with a teammate, or pasting into a postmortem. Columns: `job_id, cli_id, cli_args_json, status, exit_code, started_at_iso, failed_at_iso, duration, stderr_count, pinned`. Row order matches the drawer's newest-first sort. Cells properly RFC-4180 quoted (commas, quotes, newlines escaped). Disabled when history is empty. Uses the same client-side blob-URL pattern as CliRunner's "Download .log" - no server roundtrip, the export is whatever the user currently sees in the drawer.
- **Same WS heartbeat on `/ws/agent/{thread_id}`, plus shared helper module.** Extracted the heartbeat into `api/_ws_heartbeat.py` (exports `WS_PING_INTERVAL_S` + `spawn_heartbeat(ws, lock, disconnected)`) and used it from `jobs_ws` and `agent_ws`. `v2_ws` already implements a client-driven ping/pong pattern so no change there. `jobs_ws` keeps its `WS_PING_INTERVAL_S` re-export so the existing patch-the-attr regression test still works (the authoritative value lives in the helper module). All three streaming surfaces now have uniform idle-survival behavior - long agent threads stuck on user confirmation no longer get reaped by NAT timeouts.
- **WebSocket heartbeat on `/ws/jobs/{id}`.** Long evals that sit in a single LLM call for minutes without producing output were vulnerable to silent connection death: many NATs/proxies (60-120s on cloud LBs, as low as 60s on corporate proxies) close idle TCP connections. Now the server emits `{"type":"ping","ts":<unix>}` every 25s while the connection is alive, keeping it warm. Frame is parsed by the FE's existing JSON path and discarded by the if/else chain (no matching branch) - no client change required. Heartbeat task shares the same `send_lock` as the event-fanout loop so a ping never interleaves into a partial frame, and is cancelled cleanly alongside the reader on disconnect. Configurable via `WS_PING_INTERVAL_S`. One regression test patches the interval to 50ms and verifies a ping arrives within 10 frames on an idle long-running job.
- **`/` hotkey focuses the new CliRunner output filter.** Mirrors the drawer's pattern - press `/` outside any input/textarea and the cursor lands in the filter box. Two-step Escape: first press clears the filter, second press blurs back to the runner body so the parent's existing Escape-closes-runner handler can take over (the input's `e.stopPropagation()` on the first press prevents the window listener from closing mid-clear). Help overlay's context-shortcuts list updated: "Focus search (drawer or output filter)".
- **Free-text output filter in the CliRunner toolbar.** Customer pain: 1000+ streamed lines and browser Ctrl+F doesn't survive scroll/streaming additions cleanly. Now a small `Filter output...` input lives in the output toolbar; visibleLines AND-combines with the stderr-only chip. Substring match (case-insensitive). Debounced 150ms so heavy-output runs don't refilter on every keystroke. `N/M` count chip turns red when zero match (so an empty result is obviously the filter, not a missing job). Hidden when there are no lines yet (no useless empty input). System lines (truncation markers etc) are kept by the kind-filter but participate in the text-filter so a user grep-ing for "ERROR" doesn't get a `[server dropped 50 lines]` mark counted as a match.
- **"Copy log URL" button now appends `&include_meta=1`.** Closes the share-flow loop with the new `?include_meta=1` endpoint shipped this tick. Recipient clicks the pasted link, downloads a log file with a `# job_id / cli / started_at / status / exit_code / scope` header at the top - no need for chat context to tell what run produced it. Backwards-compatible: anyone who already has an old copied URL bookmarked still works (just without the header).
- **Search filter on the ExperimentsList page.** Customer pain: with 50+ runs in the lineage stream, finding "the run named with-fewshot-v2" or "@daisy's runs from yesterday" required manual scrolling. Now a search input lives next to the saved-view chips. Substring match (case-insensitive) against `id, name, author, tags`. AND-combines with the existing saved-view chip (week / gate / all). Debounced 120ms. `N/M` count chip turns red when zero match. `sessionStorage`-persisted query (key `evalyn:experiments:searchQuery`) so a tab switch doesn't lose the filter, mirroring the drawer pattern. `sessionStorage` (not `localStorage`) is the right TTL: filters clear on tab close, not next week.
- **"Download .md" button on the Reports page.** Companion to the existing "Copy markdown" button. Saves the report body as `evalyn-weekly-<isots>.md` so users can attach it to a wiki page, commit it to a repo, or import it into another doc tool without going through clipboard. Same blob-URL pattern as the CliRunner's "Download .log" and the drawer's "Export CSV". Timestamp in the filename keeps multiple weekly snapshots from clobbering each other in Downloads.
- **Drawer search query persists across reopens in the same tab session.** Customer scenario: user types `compare` to find their compare runs, closes the drawer to look at something else, reopens - the search box was empty before this change. Now it's mirrored to `sessionStorage` (key `evalyn:v2:jobsDrawer:searchQuery`) so the next open within the same tab session restores the query. `sessionStorage` (not `localStorage`) is the right TTL: filters are transient state that should clear on tab close, not carry into next week's session. Best-effort: quota / private-mode failures fall back to in-memory only. Empty input removes the entry rather than persisting `""` (cleaner storage).
- **Capacity chip has a 3rd "approaching cap" warning tier.** Previously the chip went straight from muted slate to ember-at-saturation. Now it shows a yellow "approaching" state when running >= ceil(0.75 * max_concurrent) but still under the cap. Customer-cared for SREs/ops watching saturation BEFORE it bites - the difference between "you have one slot left" and "queue is full" matters in practice. Tooltip text differentiates: `${N} / ${M} running` (normal), `Approaching cap: ${N} / ${M} running` (warn), `At capacity: ${N} / ${M} running. New runs will queue.` (saturated). Computed as a single tier ('normal'|'warn'|'saturated') so future tweaks (different thresholds, additional tiers) are one place.
- **Per-row "↓" log download in the Recent Jobs drawer.** Companion to the server-side `output_url` field shipped this tick. Each terminal row (and live running rows) gets a small download icon that opens `…/output.txt?download=1&include_meta=1` directly. Browser saves the log file with the self-describing `# job_id / cli / started_at / ...` header from the recent backend `?include_meta` work. URL constructed client-side (matches the server's `_output_url_for()` format) so the drawer doesn't need a server roundtrip just to render the icon. Hidden for queued (no output yet) and unknown (backend evicted record - the URL would 404). Click stops propagation so it doesn't also fire the row's "open in runner" handler.
- **Stricter validation on `/api/jobs/recent` filter params.** Two improvements: (a) `?cli_id=foo,bar` (with embedded commas) now returns 400 with a hint pointing at `?cli_ids=foo,bar` - previously this silently filtered for the literal string "foo,bar" matching no row; (b) `?since=Infinity` and `?since=NaN` now return 400 with "must be a finite number" - FastAPI's float coercion accepts these but they're nonsense for a timestamp filter and would attempt a SQL comparison on inf otherwise. Two regression tests cover both cases.
- **`last_event_at` field on agent thread metadata.** Useful for "is this thread stuck?" detection: a thread with `has_pending_confirmation=True` AND a stale `last_event_at` is awaiting user action; one with a fresh timestamp is mid-turn. Without this field, a polling client had no way to distinguish idle from active. Unix epoch float (or `null` when the thread has no events yet, e.g. fresh from `create_thread()`). Surfaces on both `GET /api/agent/threads` (listing) and `GET /api/agent/threads/{id}` (single fetch) since both share `_thread_to_dict`. One regression test covers the empty-thread null case AND the post-turn fresh-timestamp case.
- **`GET /api/agent/threads/{id}/messages` returns the conversation text.** Useful when a client wants the assistant's answers without setting up a WebSocket subscription - e.g. an agent-runner test harness, a CLI tool scripting around the dashboard, or a scheduled report capturing thread snapshots. New `AgentRuntime.thread_messages(id)` public helper returns user + assistant message bodies (system prompt filtered out so the endpoint doesn't leak prompt text). Tool-call structure inside assistant messages is preserved as-is. 404 on unknown thread, 503 when agent_runtime missing (consistent with chat/list/delete endpoints). Three regression tests cover the happy path (after a turn drives a user+assistant exchange), unknown-id, and missing-runtime.
- **`output_url` field on every job in `/api/jobs/recent` and `/api/jobs/{id}`.** Customer-cared API ergonomics: lets a FE render a "↓ log" link per row without reconstructing the `/output.txt?download=1&include_meta=1` convention, and lets external integrations (curl wrappers, Slack bots, log forwarders) paste a share-ready URL without knowing the convention. Returned as a relative URL (e.g. `/api/jobs/abc.../output.txt?download=1&include_meta=1`); the FE prepends `window.location.origin` when sharing externally. New `_output_url_for(job_id)` helper centralizes the format so future tweaks (e.g. switching the share-URL shape) are one-place. Two regression tests cover the field on both list and singular endpoints. Empty `output_url` for persisted rows with missing `job_id` (defensive).
- **`?include_meta=1` on `/output.txt` prepends a self-describing header.** Customer scenario: user downloads a log file, opens it a week later, can't tell which run produced it. Now `?include_meta=1` (off by default - existing curl users see no change) prepends `#`-prefixed comment lines: `# evalyn job log`, `# job_id: ...`, `# cli: run-eval`, `# started_at: ...`, `# ended_at: ...`, `# status: complete`, `# exit_code: 0`, `# scope: stream=stderr, tail=3`. Header is `#`-prefixed so most log tools (`less`, `awk`, `grep`) treat them as comments without intervention. Reads in-memory job state when present, falls back to persisted row, returns empty header when neither (shouldn't be observable since the body itself 404s in that case). Two regression tests cover the off-by-default no-header path and the on-with-filters scope reporting.
- **`?download=1` on `/api/jobs/{id}/output.txt` adds a Content-Disposition header.** Useful for shareable / bookmarkable download URLs: `/api/jobs/abc.../output.txt?download=1` is a permalink that browsers save as a file rather than render inline. Filename derives from the first 8 chars of the `job_id` plus the active filters: `evalyn-job-abcd1234.log`, `evalyn-job-abcd1234-stderr.log`, `evalyn-job-abcd1234-stderr-tail3.log`. The suffix encoding means concurrent downloads of different slices of the same job don't clobber each other in the Downloads folder. Two regression tests cover the no-download / with-download shape and the filter-suffix encoding.
- **"Test all configured" bulk health-check on Settings.** Customer-cared admin scenario: user has multiple providers configured (OpenAI + Anthropic + Ollama) and wants a single click to verify which still work after a key rotation, base-URL change, or model deprecation. New `BulkTestCard` between the active-provider selector and the per-provider list. Iterates configured providers (`is_set=true`) sequentially - rate-limit errors don't cascade across providers, results land top-down in run order which reads naturally, and one slow probe (cold ollama) doesn't visually bottleneck the rest (the spinner says exactly which one is in flight). Per-provider results render as `✓ openai connection ok` / `✗ anthropic rate limit`. Hidden entirely when no providers are configured (nothing to test).
- **"copy" affordance on the form-mode preview line too.** The previous commit added "Copy command" to the post-spawn output toolbar; this completes the story by adding a small `copy` button to the form-mode `PreviewLine` (the collapsed `▸ evalyn ...` line above the form). Restructured `PreviewLine` from a single `<button>` (toggle-only) into a `<div>` containing two siblings: the toggle button (left, expand/collapse) and the copy button (right, click-to-copy). `e.stopPropagation()` on the copy click so it doesn't also toggle expand. Independent local copy state with the same `idle / copied / error` pattern other copy affordances use. Now the affordance to grab the assembled shell command exists from the moment the user fills the form, not only after spawn.
- **"Copy command" button in the CliRunner output toolbar.** Customer-cared scenario: user runs `evalyn run-eval --dataset frosty --metric accuracy --limit 50` in the dashboard and wants to paste the same command into their terminal for a quick rerun. The preview line at the top of the output already shows the assembled command but rendered as text; now a one-click button copies the exact `evalyn ...` string (without the `$` sigil so paste works directly). Independent copy state from "Copy ID" / "Copy output" so each button reports its own success/failure. Visible whenever there's a preview to copy (form mode AND post-spawn output view), so the affordance exists from the moment the user fills the form.
- **Per-thread CoPilot draft persistence on the full `/copilot` route too.** Mirrors the dock implementation: on-mount load, 250ms-debounced save, synchronous clear on submit, thread-switch reload. Same shared `copilotDrafts.ts` storage so a draft typed in the dock is restored when the user expands to the full route, and vice versa - the textarea on each surface reads from the same per-threadId key.
- **Per-thread CoPilot draft persistence.** Composes with the form-drafts pattern shipped earlier this loop. Customer scenario: user types a long question into the dock, accidentally refreshes / closes-and-reopens, draft is gone. Now: every keystroke debounces 250ms and persists to localStorage keyed by `threadId` (or `__new__` for the pre-thread state). On mount the textarea restores the saved draft. On submit the draft is cleared synchronously (avoids a race between the debounced save and the navigate-after-send that would otherwise re-persist a stale draft if `threadId` changes mid-flight). Switching threads loads that thread's draft - one open dock can accumulate one draft per thread without interference. New `copilotDrafts.ts` mirrors `cliRunnerDrafts.ts` (LRU cap of 20 threads, quota-failure-tolerant).
- **`agent_threads` + `agent_open_threads` fields in `GET /api/health`.** Composes naturally with the `running` / `max_concurrent` fields shipped earlier this loop: a single curl now surfaces both job pressure AND agent activity, so an SRE dashboard can alert on stuck agents (`open > 0` for a sustained period) the same way it alerts on saturated job slots. New `AgentRuntime.thread_counts()` returns `{total, open}` (open excludes threads whose `final` has fired). Helper is public so server.py doesn't reach into `_threads` and break under future restructuring. Best-effort: if `agent_runtime` is missing or the inspection raises, both fields report 0 (the healthcheck never fails closed on a degraded agent system).
- **Day-group headers in the Recent Jobs drawer.** A 30-entry history spanning multiple days now reads at a glance: thin uppercase dividers ("★ Pinned", "Today", "Yesterday", "Mar 5", or "Mar 5, 2025" for cross-year) precede the first row of each group. Pinned entries collapse into a single "★ Pinned" header (regardless of run date) since their grouping signal is the star, not the date. Unpinned entries fall into newest-first date groups. Implementation centralized as a `renderRowsWithDayHeaders` helper plus a `dayHeaderLabel` pure function so the grouping logic is testable in isolation if we want unit coverage later.
- **`running` + `max_concurrent` fields in `GET /api/health`.** Useful for SRE dashboards that want to alert on saturation: `running >= max_concurrent` for sustained periods is a signal the cap should be raised or the workload spread. Best-effort - if `job_manager` isn't yet attached (early startup race) or the inspection raises, we report zeros rather than failing the healthcheck. The endpoint MUST stay reachable even when the job system is degraded; that's its whole point. Three regression tests cover the new fields, the idle-zero shape, and the missing-job_manager fallback.
- **Browser notifications when a backgrounded job finishes.** Customer-cared scenario: user kicks off a long eval, switches to Slack / docs / another tab, and currently has to remember to come check. Now: when a job reaches a terminal state AND the dashboard tab is hidden AND the user has granted permission, an OS notification surfaces "run-eval finished (45s, exit 0)". Click the notification to focus the dashboard. New `frontend/src/v2/notifications.ts` wraps the Notification API with feature-detection, hidden-tab gating, per-`job_id` `tag` (so a queued -> failed sequence replaces rather than stacks), and silent-on-success / beep-on-failure. CliRunner's terminal-status handler calls `notifyJobTerminal`. Drawer header shows "Enable notifications" only when permission state is `'default'`; once granted/denied the affordance disappears (re-prompting is browser-blocked anyway). All API calls are wrapped in defensive guards so unsupported browsers (older Safari, embedded webviews) report `'denied'` instead of throwing.
- **"Copy ID" button in the CliRunner output toolbar.** Click copies the active `job_id` to clipboard with a transient `✓ ID copied` confirmation. Useful for filing support tickets, grep-ing server logs, or sharing a specific run with a teammate. Visible only when a job has been spawned (no button before Run, none for resumed-from-history rows whose ID is already there). Independent copy state from "Copy output" so a successful output copy doesn't tint the ID button (and vice versa). Truncated id in the tooltip (`Copy job ID (abc12345...)`); aria-label has the full ID for screen readers.
- **Pin a job to keep it in history forever.** Power-user feature for "I want to keep this reference run around even after I do dozens of new ones". Star button on every drawer row toggles `pinned` on the localStorage entry. Pinned entries (1) survive the 30-entry history cap (cap applies only to unpinned), (2) sort to the top of the drawer regardless of age, and (3) survive "Clear" (it now drops only unpinned; the user has to explicitly unpin before clearing). New `setJobPinned(jobId, pinned)` helper. `JobHistoryEntry.pinned?: boolean` is the persisted field. The pin glyph slot uses ★ (filled, ember) vs ☆ (outline, dim) so toggling never shifts row layout.
- **"Reset" button in CliRunner when the form has been edited.** Complements the new form drafts: with edits persisted, users occasionally want a one-click way to undo and start fresh. Reset rolls values back to the form's opening state (schema defaults + draft + seed - the same priority chain `initialValues` captures) and clears the persisted draft so the next open is a clean slate rather than an immediate restore of what the user just discarded. Hidden when the form is pristine (`isDirty=false`) so a fresh form doesn't carry visual noise. Placed left of the existing Cancel/Run buttons for the standard "destructive-ish action on the left" reading order.
- **Args summary line on every Recent Jobs row.** Closes the visibility gap where 5 `compare` or `run-eval` rows looked identical and the user had to hover each one for the tooltip to disambiguate. Reuses the existing `previewCommand` (with the `evalyn <cli_id>` prefix stripped so it doesn't repeat the row's primary line). Mono font, dimmed, single-line with text-overflow ellipsis - long arg strings stay readable without breaking row height. Hidden entirely when the run had no args (no useless empty line).
- **Text search filter in the Recent Jobs drawer.** Power-user feature for "show me my last `compare` runs" or "find that one with `--limit 200`". Substring match (case-insensitive) against `cli_id` plus a JSON dump of `cli_args`, debounced 120ms so a long history isn't refiltered on every keystroke. AND-combines with the failure filter. `/` focuses the input (skips when focus is already in another input/textarea so it doesn't intercept normal typing). Two-step Escape: first press clears the search, second closes the drawer (matches Spotlight/cmd-palette idiom). Match count surfaces below the input when a query is active so an empty result set is obviously the filter and not a missing job. Search row is hidden when history is empty so first-time users don't see a useless filter box.
- **Tab title shows the cli_id when exactly one job is running.** Existing pattern is `(N) Evalyn` for any active job count. With one job, that's now `(1) run-eval Evalyn` (or whichever cli_id) so a user with multiple browser tabs can tell which command is running where without switching focus. With zero or 2+ active jobs, we fall back to the bare count to avoid arbitrarily picking one to highlight. New `activeJobCliId(entries)` helper in `jobsHistory.ts` returns the single-active cli_id or null. The composition is unchanged: "(running) !failed base".
- **Per-command CliRunner form drafts auto-saved to localStorage.** Customer-cared scenario: user opens the runner for `run-eval`, fills 5 fields, gets pulled into Slack for 10 minutes, comes back to find an empty form. Now: every input change debounces 300ms and persists to a small LRU keyed by `cli_id` (cap 30 commands, oldest evicted). New `cliRunnerDrafts.ts` with `loadDraft`/`saveDraft`/`clearDraft`. Priority order on form init: schema default -> persisted draft -> caller-provided seed -> user edits. Seed wins over draft so explicit intent (deep links, "Re-run with same args" prefill from the drawer) isn't shadowed by stale state from a prior session. Suppressed entirely in resume mode (form not visible). Draft is cleared on successful spawn so the next open is a clean slate rather than restoring last-run's values into what the user might think is a fresh form. Quota / private-mode failures are tolerated silently - drafts are best-effort, never load-bearing.

### Tests

- **Integration test for the VACUUM-on-shutdown lifespan hook.** The standalone `JobPersistence.vacuum()` already had unit coverage but the wiring (`@app.on_event("shutdown")` calling it) didn't. Without an integration test, a future refactor that drops the hook would silently regress disk-space recovery on long-running dashboards. Test uses `TestClient` as a context manager (which fires the full startup + shutdown lifespan) and a counter wrapper around the persistence's `vacuum()` to verify it's called exactly once on exit.
- **Regression test for the agent WS heartbeat.** Mirrors the jobs WS heartbeat test from a few ticks ago. Patches `WS_PING_INTERVAL_S` in the shared `_ws_heartbeat` helper module to 50ms, opens a WS to a freshly-created idle agent thread (no chat post), verifies at least one `{"type":"ping"}` frame arrives within 10 receives. Pins the contract that the shared helper is wired into BOTH `jobs_ws` and `agent_ws` - if a future refactor breaks one without breaking the other, this test catches it.
- **Unit tests for `notifications.ts` permission + visibility gating.** 11 tests pin the three-gate contract: API supported, `permission === 'granted'`, `document.visibilityState === 'hidden'`. Exercises both the unsupported path (jsdom default - no `Notification` global) and the supported path (`vi.stubGlobal` with a mock constructor + permission state). Specific assertions: silent=true for `complete`, silent=false for `failed`, per-`job_id` tag so queued→failed replaces rather than stacks, body string includes `exit N` and `Ns`. Exit-code and duration in the formatted body. 81/81 FE tests pass across 12 files.
- **Unit tests for `cliRunnerDrafts.ts`.** Sibling to copilotDrafts but with deliberately different semantics (`Record<string, unknown>` not string; "empty form" is a valid persisted draft; empty `cliId` is a no-op rather than synthetic shared bucket; `loadDraft` returns null on miss not ""). 13 tests pin those distinctions explicitly so a future refactor that tries to "unify" the two modules has a clear failure signal. 70/70 FE tests pass across 11 files.
- **Unit tests for `copilotDrafts.ts` LRU + per-thread semantics.** Same shape as cliRunnerDrafts (which we don't test yet); both came from the same per-context drafts pattern. 11 tests across 5 describe blocks: round-trip per threadId, the `__new__` pre-thread key (null/undefined/empty all bucket together but don't bleed into named threads), `clearCoPilotDraft` removes the entry entirely + empty-string save also removes, LRU cap evicts oldest at MAX_DRAFTS=20, save promotes a re-saved threadId to most-recently-used, corruption tolerance (poisoned JSON / wrong-shape store both return empty rather than throwing). 57/57 FE tests pass.
- **Unit tests for `jobsHistory.ts` pin / cap / sort semantics.** 11 tests cover the localStorage layer that several recent features (pinning, day headers, history filter) depend on. Specifically: cap drops oldest unpinned but preserves pinned even when pins exceed the cap; `sortNewestFirst` puts pinned above unpinned regardless of age; `setJobPinned` toggles cleanly and is a no-op for unknown ids; `clearJobsHistory` preserves pinned and fully clears when no pins; `activeJobCliId` returns the cli_id only when exactly one job is active. Pure-function tests against jsdom's localStorage - no React. Each test resets the relevant storage key in `beforeEach` so order doesn't matter.

### Performance

- **Forward-migration regression test for composite indexes.** Pins that an existing pre-composite-index `jobs.sqlite` (from before this loop) picks up the new indexes on next startup, not just fresh DBs. Hand-crafts a legacy DB shape (table + only the original single-column index), opens it with `JobPersistence`, asserts all three indexes exist after init. Mirrors the existing `test_persistence_migrates_stderr_count_into_existing_db` test that pinned the column-add migration. Without this test, a future refactor that moved index creation behind a "fresh DB only" guard would silently regress query performance for everyone with an existing DB.
- **Composite SQLite indexes on `jobs(cli_id, started_at_iso)` and `jobs(status, started_at_iso)`.** Without these, a `?cli_id=run-eval&limit=50` filter on a persistence table with thousands of rows would scan in started_at order and discard non-matches. With the composites, SQLite seeks directly to the cli_id (or status) prefix and walks in started_at order. New `_COMPOSITE_INDEXES` tuple, created via `IF NOT EXISTS` so re-running on existing DBs is a no-op. The original single-column `idx_jobs_started_at` stays useful for unfiltered queries and `?since`/`?before`-only windowed queries. Two regression tests: `EXPLAIN QUERY PLAN` confirms the planner picks the composite for filtered+ordered queries; `sqlite_master` lookup verifies all three indexes exist after init.
- **Idle-prefetch the newly-lazy overlay chunks.** Closes the perceived-delay gap from the previous commit. Without this, the FIRST Cmd+K / FAB click would visibly pause for 50-200ms while the chunk fetched. Now an `useEffect` in AppShell schedules `void import(...)` for all three overlays via `requestIdleCallback` (where available, falls back to `setTimeout(0)` for Safari). The chunks land in the browser cache during the post-paint quiet window so the first open is instant. Doesn't compete with initial route render because idle-callback runs only when the main thread is otherwise free. CliRunner counts stderr lines from the raw stream (so the true total survives the visible buffer's MAX_OUTPUT_LINES ring trim) and persists it on every terminal-status patch. Drawer rows now render a "5 stderr" inline chip alongside the exit-code metadata when the count is positive — useful for spotting noisy jobs even when exit code 0. Counter resets on Re-run.
- **Row tooltips in RecentJobsDrawer show the full preview command.** Hovering a row used to surface only the opaque `job_id` ("a8f3..."); now it shows the full argv ("evalyn run-eval --dataset path --metric f1 --limit 100"), so users can disambiguate similar runs without opening them. The `previewCommand` helper that builds this string was extracted from CliRunner into the shared `v2/api/cli.ts` so both surfaces use the same formatting (skip empty/null/undefined, drop false booleans, unfold array values into multiple positionals).
- **Visible "Reconnecting…" pill in the co-pilot dock during agent WS retry.** Mirrors the CliRunner reconnect indicator from the previous tick. `subscribeAgent` gained `onReconnecting` / `onReconnected` callbacks; `useCoPilotThread` debounces them through a 1.5s timer and exposes a `reconnecting` boolean. CoPilotDock renders the same ember-coloured pill in its header next to the turn count when reconnecting is active. Brief blips stay invisible; longer recoveries are surfaced so the user knows a quiet chat is recovering, not hung. Cleanup paths (thread reset, hook detach, max-attempts give up) all clear the timer + state.
- **Visible "Reconnecting…" pill in CliRunner during WS retry.** The auto-reconnect work in earlier ticks made transient WS disconnects invisible — but a long retry window (up to 23s with 5 attempts) could be confusing: the user sees a gap in output and may suspect a hung eval. CliRunner now surfaces a small ember-coloured "Reconnecting…" pill in the output preview row when a disconnect lasts past 1.5s, hiding the cosmetic flash for blips we recover from quickly. Pill clears as soon as the WS reconnects successfully or the user hits Re-run / leaves the runner. Implemented via two new `subscribeJob` callbacks (`onReconnecting`, `onReconnected`); each fires with try/catch so a consumer throw cannot kill the reconnect path.
- **Cancel button on running rows in RecentJobsDrawer.** Symmetric to the Re-run button on terminal rows. Each queued/running row now shows a small `✕` button on the right edge; click sends SIGTERM via the existing `/api/jobs/{id}/cancel` endpoint and optimistically patches the local entry to `cancelled`. Previously, the only way to cancel a still-running job was to navigate back to the CliRunner instance — if that runner was already closed (user moved on), the job ran to completion regardless. The button is disabled with a `wait` cursor while the cancel HTTP is in flight so a double-click does not fire two cancels. On HTTP failure (network down, 404 because the job already finished between click and request), the row falls back to a snapshot refresh so its status reflects whatever the server actually thinks.
- **Re-run button on RecentJobsDrawer rows.** Each terminal job row (complete / failed / cancelled) now shows a small `↻` button on the right edge that opens the CliRunner with the row's args pre-filled but no `resumeJobId`, dropping the user on the form one Run-click away from a fresh launch. Previously the only path was: click row → CliRunner opens in resume mode → click "Re-run" inside. The row layout was refactored from a single `<button>` to a flex container with two sibling `<button>`s (resume + re-run) so the inner button is valid HTML; hover state moves to the wrapper so the whole row still highlights together. Hidden for queued/running rows (a live job already exists) and for the `unknown` evicted state. Falls back to the resume click if the cli_id is no longer in the catalog (re-run needs a real schema to render the form).
- **Tab title surfaces unacknowledged failures.** The AppShell title prefix already shows `(N)` when jobs are running; it now also appends `!N` when N recent jobs failed since the user last opened the Recent Jobs drawer (e.g. `(1) !2 Eval · Evalyn`). Backed by a new `failed_at_iso` field stamped on first status-transition to `failed` and a localStorage `ACK_KEY` timestamp updated whenever the drawer opens. Cross-tab synced via the `storage` event so opening the drawer in one tab clears the badge in others. Lets a user on another browser tab notice an overnight or background-tab eval failure without having to click into the dashboard.
- **Failed-jobs filter chip in RecentJobsDrawer header.** The drawer keeps up to 30 recent jobs in local history; spotting which ones failed used to mean scanning every status pill. A new clickable chip in the header (`X failed`) appears whenever any row's status is `failed` and toggles a "show failed only" filter, mirroring the pattern from the CliRunner stderr chip. The filter excludes `cancelled` (user-driven) and `unknown` (server-evicted) since neither is an unexpected failure. Auto-clears when the failed count drops to 0 so the chip never disappears mid-filter and strands the user with an empty list. A defensive empty-state covers the brief race window between toggle and auto-clear.
- **Jump-to-first-error button in CliRunner output header.** When stderr exists and the filter is off, a small `↥ first` button next to the stderr-count chip scrolls the first stderr line into view (`scrollIntoView` with `block: 'center'`) so the user can locate the first failure point without losing the surrounding stdout chronology. Hidden when the filter is on (the first error is already on screen) or when stderr is empty. Companion to the click-to-filter chip below: filter for "show only errors", jump-to-first for "show me where it started" while keeping context.
- **Click-to-filter stderr in CliRunner output.** The stderr-count chip in the CliRunner output header is now interactive: click it to filter the visible output to stderr (and system) lines only, click again to show all output. The chip's style (filled background, bold weight, leading checkmark) reflects whether the filter is active. A dedicated empty-state shows "No stderr lines yet" when the filter is on and nothing matches, instead of the default "(no output)" which would be misleading. The Copy button continues to copy ALL lines regardless of the filter — the filter is for scanning, the clipboard is for sharing. The filter auto-clears whenever the stderr count drops to 0 (terminal status with no errors, or all stderr evicted from the ring buffer mid-run) so the user can never get stuck with a stale filter when the chip itself is no longer rendered. Lets users find a buried failure in a chatty eval in one click instead of manual scrolling.

### Performance

- **`subscribeAgent` auto-reconnects on unexpected close with `?since=N` cursor.** Symmetric to the prior `subscribeJob` reliability work, applied to the chat WebSocket. Network blips, dev-server restarts, and brief disconnects mid-conversation no longer leave the co-pilot stream dead; the WS retries with exponential backoff (1s → 2s → 4s → 8s → 8s, max 5 attempts) and forwards `?since=lastSeenEventId` so the backend skips events the consumer already saw — no duplicate text-deltas, no missing tool-call cards. The `onOpen` handler fires on first connect only so reconnects do not double-fire it; `onClose` is suppressed for intermediate disconnects we recover from. After 5 failed attempts, `onError` fires with a clear "Lost agent stream after 5 reconnect attempts" message. Bonus: separated the JSON-parse and `onMessage`-throw error paths so the console message accurately names the failure mode (the previous code labelled both as "agent ws json parse error"). Existing callers benefit transparently — no API change.
- **`subscribeJob` auto-reconnects on unexpected close with `?since=N` cursor.** Network blips, dev-server restarts, and brief disconnects mid-stream used to leave CliRunner stuck on a "Lost connection to job stream" toast; the user had to refresh the page to resume tailing. The WS subscriber now retries with exponential backoff (1s → 2s → 4s → 8s → 8s, max 5 attempts ≈ 23s patience) and passes the highest observed `event_id` as `?since=N` so the backend replays only events the client has not yet seen — no duplicate lines, no missing lines. The "running" onStatus pill fires on first connect only, so a reconnect after the user clicked Cancel does not flip the UI back to running. `onClose` is suppressed for intermediate disconnects we recover from, then fires once on terminal close (user-initiated, server-delivered exit, or attempts exhausted). After 5 failed attempts, `onError` fires with a clear "Lost job stream after 5 reconnect attempts" message. Existing callers benefit transparently — no API change.
- **Co-pilot chat text-delta batching via requestAnimationFrame.** The streaming agent reply previously called `setMessages` per token (~80/sec for Sonnet, faster for Haiku), each rebuilding the messages array, the agent bubble, and concatenating bubble text. `useCoPilotThread` now coalesces deltas into a `Map<messageId, accumulatedText>` ref and flushes once per animation frame, so the chat re-renders at most ~60Hz regardless of token rate. Other event kinds (tool_call_*, final, error) pass through directly. The `final` event force-flushes pending deltas before applying its patch so the bubble's text is current and never "rewinds" mid-stream. WS reconnect, thread reset, and unmount all cancel pending rAF and clear the buffer to prevent stale tokens leaking into a new conversation.
- **CliRunner WS line batching via requestAnimationFrame.** Chatty eval runs (100s of stdout lines/sec) used to call `setLines` once per WebSocket message, triggering one React render per line. CliRunner now buffers lines in a ref and flushes once per animation frame (`requestAnimationFrame`), capping render rate at ~60Hz regardless of line rate. The buffer is bounded at `MAX_OUTPUT_LINES` so a backgrounded tab cannot accumulate unbounded memory while rAF is paused. Cleanup on unmount and Re-run cancels any pending frame and clears stale lines so they do not bleed into a new run. No visible behavior change for slow streams; high-rate streams stop juddering.

### Changed

- **RecentJobsDrawer's "show failed only" filter is now persistent.** The chip state lives in localStorage under `evalyn:v2:jobsDrawer:failureFilter`, so a user who toggles "show failed only" while tracking a regression across multiple eval iterations stays in that mode after a page refresh. The auto-clear path (failed count drops to 0) clears the localStorage entry too, so an accidentally-armed filter never ghosts across sessions.
- **`subscribeJob` reconnect-with-cursor.** `dashboard/frontend/src/v2/api/jobs.ts::subscribeJob` now accepts an optional `{ since }` option and forwards it as `?since=N` on the `/ws/jobs/{id}` URL; the backend's existing `since` support means a reconnecting client can skip events with `event_id <= since`. `JobLine` gained an optional `event_id` field carrying the server-assigned monotonic id, so callers can track the high-water mark and pass it back on reconnect to avoid re-receiving already-displayed lines. Additive: no behavior change for current callers.

The current shared WS in `v2/api/v2ws.ts` already implements the recommended `_ws === ws` close-handler guard. Cleaned up the entry so future maintainers do not chase a non-existent bug.

### Fixed

- **Backend job-persistence sqlite mirror was growing unboundedly.** `JobPersistence.delete_old()` was defined but never called by any caller, so every spawned job permanently added a row to `.evalyn/data/jobs.sqlite`. Over months of use the file would grow to MBs and `/api/jobs/recent` queries would slow proportionally. `JobManager` now invokes `_persist_gc_maybe()` at the end of every `_persist_job_terminal`; it counts terminal events and prunes the table to the most-recent `persistence_keep` rows (default 200) every `persistence_gc_interval` terminals (default 50). Both are tunable via constructor args. GC runs in its own try/except so a prune failure cannot poison the per-job persist path. Adds three regression tests: GC fires on terminal at threshold, GC is skipped below the interval, and GC is a safe no-op when persistence is disabled.
- **Subscriber race in `AgentRuntime.subscribe()`** (KNOWN_ISSUES.md #3). Same pattern as the JobManager fix below: `_AgentEventStream` gained a replay phase with `_live_buffer`, `_replay_put`, `_begin_replay`, `_end_replay`. `AgentRuntime.subscribe` now registers the stream BEFORE replay, snapshots `_next_event_id`, replays via `_replay_put` (bypasses the buffer), and flushes concurrent `_emit` events at the end. Confirmation_required events emitted during the previous registration gap are no longer dropped; the chat UI cannot get stuck waiting for them.
- **Subscriber race in `JobManager.subscribe()`** (KNOWN_ISSUES.md #1). Live job events emitted between the replay phase and subscriber registration could be silently dropped on slow or freshly-attached WebSocket clients. `_EventStream` now buffers concurrent `_emit()` events into `_live_buffer` during replay; `subscribe()` registers the stream first, snapshots `_next_event_id`, replays from the snapshot, then flushes the buffer in order. Result: no event loss and no out-of-order delivery, even if future changes make queue puts yield mid-replay.

## [0.1.0] - 2026-05-01

Initial release. Localhost IDE for evalyn evaluations, distributed as a separate optional package.

### Added

- **CLI catalog** - all 35 evalyn CLIs introspected from their argparse parsers and exposed as auto-generated forms. Groups: Tracing, Dataset, Metrics, Eval, Analysis, Annotation, Insights, Export, Simulation, Infrastructure, Quickstart.
- **Auto-form generation** - 7 param kinds (`bool`, `string`, `number`, `select`, `multiselect`, `path`, `long-text`) classified from argparse `Action` shape and dest-name heuristics. Three form modes: Form, Preview, Raw.
- **Subprocess streaming** - `JobManager` spawns each CLI as `["evalyn", <cmd>, ...]` via `asyncio.create_subprocess_exec`. Per-line stdout/stderr capture, fanout subscribe for multiple WebSocket viewers, backpressure with truncation marker, SIGTERM + 3s grace + SIGKILL on cancel, 60min default timeout, last 100 jobs retained in memory.
- **Terminal panel** - inline ~1KB ANSI parser, auto-scroll, one terminal view per job tab.
- **Jobs panel** - live state of running and recent jobs, click-to-open, per-row cancel.
- **AI chat agent** - dock-right `ChatPanel` with full agentic loop: text streaming, tool-call cards, confirmation cards (approve/reject), final-suggestion cards (clickable into pre-filled CLI form). Per-turn budget of 8 tool calls.
- **Multi-provider support** - `OpenAIProvider`, `AnthropicProvider`, `OllamaProvider` behind a shared `BaseProvider` interface. Provider-native tool-call streaming.
- **Credentials store** - `~/.evalyn/credentials.json` with atomic write and `chmod 600`. API never returns plaintext keys to the frontend. Per-provider `test` endpoint makes a 1-token completion call.
- **Settings UI** - `SettingsModal` with API-key input (password type), test button, model dropdown, active-provider radio.
- **Read-only allowlist** - 19 commands auto-run by the agent without confirmation. All other commands require explicit user approval via a confirmation card; 5min timeout defaults to rejected.
- **WebSocket transport** - `/ws/jobs/{id}` for job streams, `/ws/agent/{thread_id}` for agent events. Reconnect with `last_event_id`.
- **Localhost binding** - bound to `127.0.0.1` by default. `--unsafe-bind` required to override, with stderr warning.
- **CSRF protection** - per-server random token injected into served `index.html` as `<meta name="workbench-token">`. Required on all mutating routes via `X-Workbench-Token` header.
- **Plugin discovery** - registers the `dashboard` subcommand on core evalyn via the `evalyn.commands` entry-point group. No core changes needed at install time.
- **Pre-built frontend** - React 18 + TypeScript + Vite bundle vendored at `evalyn_dashboard/static/`. End users never run `npm`.

### Notes

- **Deprecation alias.** The previous `evalyn dashboard` command (a static HTML insights report) is renamed to `evalyn report`. When `evalyn-dashboard` is **not** installed, `evalyn dashboard` prints a stderr deprecation warning and forwards to `evalyn report`. The alias is removed in core evalyn v3.0.
